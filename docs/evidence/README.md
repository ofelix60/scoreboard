## Deploys

![ALB 5xx and request count across Sunday's deploys](deploys-alb-5xx-vs-requests.jpg)

**Load-balancer errors (blue) against requests (orange), across every Sunday deploy.**
The spike at about 00:02 is a deploy without the readiness hook: 108 502s by the load
balancer's count (106 in my once-a-second request loop) while the new instance's
container was still starting. The plateau from 03:19 to 03:45 is two deploys
through the hook under heavy traffic, one of them broken, with no 5xx at all. ELB 5xx
only has a datapoint when something failed, which is why requests are graphed with it.

![Instance refresh history](deploys-instance-refresh-history.jpg)

**Every instance refresh.** The cancelled one (07:19 PM) had a broken boot script. The
lifecycle hook kept its instance out of service, the old instance served 442 of 442
requests, and I cancelled the refresh by hand.

## An induced database outage

![ALB metrics during the outage drill](drill-alb-metrics.jpg)

**RDS stopped at 19:08, started at 19:16.** The target goes unhealthy (red, right axis)
and the app answers with a fast 503 (orange, about 18 a minute). The load balancer's own
errors (blue) stay at zero: with its only target unhealthy, the ALB fails open and keeps
routing to it. The full timeline is in the [postmortem](../postmortem-db-outage.md).

## The alarm

![Target unhealthy before the database existed](alarm-target-unhealthy-before-rds.png)

**Before RDS existed, the target failed its `/readyz` check** (`ResponseCodeMismatch`):
the app was up, but it had no database to be ready for.

![UnHealthyHostCount alarm graph](alarm-graph.png)

![Alarm history](alarm-history.png)

**The alarm caught that real problem the moment it was created.** It went into ALARM
at 19:12 and back to OK at 22:02, nine minutes after the deploy that added the database.
The two spikes to 2 are deploys, with the old and new instance briefly side by side.

## Access and secrets

![An SSM session on the instance](ssm-session-no-ssh.png)

**A shell on the instance through SSM: no SSH key, no port 22 rule.** sshd was still
listening when this was taken, and port 22 was still unreachable from outside, because
the security group drops the packets:

```
nc: connectx to 3.22.194.195 port 22 (tcp) failed: Operation timed out
```

sshd is disabled at boot now too. The security groups' inbound rules, from
`aws ec2 describe-security-groups`:

| Security group | Inbound |
|---|---|
| alb | TCP 80 from anywhere |
| app | TCP 8000 from the alb group only |
| db | TCP 5432 from the app group only |
| default | nothing |

![RDS connectivity, managed master credentials](rds-managed-secret.png)

**The database password lives in Secrets Manager, generated by RDS.** Terraform only
knows the secret's ARN. AWS's own connection example uses `sslmode=verify-full`; the
app doesn't yet (see [known gaps](../known-gaps.md#aws)).

![RDS security group rules](rds-sg-inbound-from-app-only.png)

**The database accepts connections only from the app's security group.**

## CI and image publishing

![A green CI run on a pull request](ci-green-on-a-pull-request.jpg)

**Every pull request runs three jobs:** ruff, mypy and pytest (`python`), the alert rule
checks (`prometheus`), and a full image build (`image`). The `prometheus` job runs:

```
$ promtool check config prometheus.yml
Checking prometheus.yml
  SUCCESS: 1 rule files found
 SUCCESS: prometheus.yml is valid prometheus config file syntax
Checking alerts.yml
  SUCCESS: 1 rules found

$ promtool test rules alerts_test.yml
  SUCCESS
```

The two rule tests are "fires after 5 minutes of mostly-5xx traffic" and "stays quiet
on a low-traffic service with occasional failures". Each was checked by breaking the
rule on purpose and watching the test fail.

![Merge blocked by a failing required check](ci-merge-blocked-by-failing-check.png)

**A failing required check blocks the merge button,** with no bypass for the repo owner.

![Publish run denied on another branch](oidc-denied-other-branch.jpg)

![Publish run succeeding on main](oidc-published-from-main.jpg)

**The same workflow, two branches.** From `test/oidc-deny`, AWS refused the role:
`Not authorized to perform sts:AssumeRoleWithWebIdentity`. From `main`, the image was
pushed to ECR, with no AWS keys stored in GitHub.
